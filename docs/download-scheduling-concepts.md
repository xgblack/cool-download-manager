# 下载调度概念与处理流程

> 更新日期：2026-08-29
> 适用范围：当前 Swift 原生 macOS 版本的 HTTP、HTTPS 和 HLS 下载。

本文统一下载设置、进度界面和产品说明中的概念。核心结论是：**同时下载任务数、单任务最大连接数和 Range 工作块数是三个不同的数量。** Range 工作块可以多于连接数，但同一时刻只有少量工作块会发出请求；所有任务还要共同遵守全局资源预算。

性能依据、Motrix/aria2 对比和基准结果见[下载核心性能评估](download-core-performance-evaluation.md)。

## 1. 概念口径

| 概念 | 含义 | 不代表什么 |
| --- | --- | --- |
| 下载任务 | 一个待下载的 HTTP 文件或一组 HLS 媒体内容 | 不等于一个网络连接 |
| 同时下载任务数 | 允许同时处于下载状态的任务数量，当前默认值为 3；设为 0 表示不设置全局任务数量上限 | 不等于每个任务的连接数；设为 0 也不会绕过队列和资源预算 |
| 单任务最大连接数 | 一个任务允许使用的 Range 并发上限，可设置为 1 到 64 | 不是操作系统线程数，也不保证一定建立这么多连接 |
| 当前活动 Range 请求 | 某一时刻正在传输数据的 Range 请求数量 | 不等于 Range 工作块总数；在 HTTP/2 下也不一定等于物理 TCP 连接数 |
| Range 工作块 | 文件中一段确定的字节范围，是可排队、可记录进度和可恢复的工作单元 | 不是线程，也不是始终占用连接的请求 |
| 全局 Range 连接预算 | 所有任务可同时执行的 Range 数据请求总上限，当前版本为 16 | 不是每个任务各有 16，也不是进程中所有 HTTP 请求的总上限 |

历史配置字段仍可能使用“线程数”这一内部名称，但产品和界面统一将其解释为**单任务最大连接数**。

## 2. 三个数量如何配合

下载调度可以理解为三层控制：

```text
同时下载任务数
  -> 决定有多少个任务可以进入下载状态

单任务最大连接数
  -> 限制每个任务最多能并行处理多少个 Range 工作块

全局 Range 连接预算
  -> 限制所有任务合计正在执行的 Range 数据请求数量
```

Range 工作块位于这三层控制之下。一个任务可以提前准备较多工作块，活动连接完成当前工作块后再领取下一个。因此，**足够大的新文件在最大连接数为 16 时生成 64 个 Range 工作块是正常行为，不会产生 64 个同时请求。**

当前行为可以简化为：

```text
满足 Range 条件且文件不小于 32 MiB 时：

新任务的 Range 工作块数
  = min(单任务最大连接数 x 4,
        floor(文件大小 / 16 MiB),
        128)

单任务当前活动 Range 请求数
  <= min(单任务最大连接数,
         尚未完成的 Range 工作块数)

所有任务的活动 Range 数据请求合计 <= 16
```

准备比连接更多的工作块，是为了让先完成的连接继续领取剩余工作，减少某个慢请求拖住整个文件尾部的概率。工作块数量描述的是任务被拆成多少份工作，不描述此刻用了多少连接。

## 3. 单任务最大连接数从哪里来

连接上限按以下优先级确定：

```text
任务单独设置
  > 主机单独设置
  > 全局“单任务最大连接数”设置
```

- 任务或主机显式设置了连接数时，任务从当前资源允许的所选上限开始，但传输效果变差或发生可恢复失败时仍可降低连接数。
- 只使用全局设置的自动任务通常从 1 个连接或该主机过去的稳定档位开始，再按 1、2、4、8、16 等档位逐步试探。
- 主机历史表现只影响起始档位，不会把未来任务永久限制在过去的较低值。
- 无论单任务上限设置为多少，所有任务仍共享全局 Range 预算。设置为 64 不表示当前版本允许该任务独占 64 个 Range 请求。

因此，这个设置表达的是“允许调度器最多尝试到哪里”，不是“下载开始后固定使用多少连接”。

## 4. 新 HTTP 下载的处理流程

```text
任务进入等待队列
  -> 同时下载任务数、所属队列和资源预算允许后启动
  -> 确定单任务最大连接数
  -> 判断是否启用 HTTP Range 下载
  -> 探测文件大小和服务器 Range 能力
      -> 条件不足：使用单通道下载
      -> 条件满足：创建 Range 工作块队列
  -> 活动连接领取工作块并传输
  -> 根据传输效果增加、维持或减少活动连接
  -> 工作块全部完成后结束任务
```

以下任一情况会让新任务使用单通道下载：

- 未启用 HTTP Range 下载；
- 单任务最大连接数为 1；
- 无法确定文件大小；
- 服务器不能正确处理 Range 请求；
- 文件小于 32 MiB，无法形成至少两个 16 MiB 级别的工作块。

“单通道”表示同一时刻只使用一个数据请求。首次下载通常是普通 GET；恢复未完成内容时，仍可在服务器支持的前提下用一个 Range 请求从已有位置继续。

## 5. 不同文件大小的当前策略

下表以“单任务最大连接数 = 16”的新 HTTP 任务为例。表中的“最多活动连接”还会被自动调度和剩余全局预算进一步降低。

| 文件大小 | 处理方式 | Range 工作块数 | 本任务最多活动连接 |
| --- | --- | ---: | ---: |
| 小于 32 MiB | 单通道下载 | 0 | 1 |
| 32 MiB | Range 下载 | 2 | 2 |
| 64 MiB | Range 下载 | 4 | 4 |
| 256 MiB | Range 下载 | 16 | 16 |
| 512 MiB | Range 下载 | 32 | 16 |
| 1 GiB 及以上 | Range 下载 | 64 | 16 |

这个策略体现了两点：

1. 小文件不创建多块工作队列，避免额外的 Range 数据请求、排队和多块状态管理成本。
2. 大文件增加的是待处理工作块，而不是无限增加同时连接数。连接完成一块后继续领取下一块，以有限资源维持持续传输。

16 MiB 是当前工作块的最小目标大小，16 是当前全局 Range 预算。它们是现阶段的保守工程默认值，不是适用于所有网络、服务器和磁盘的理论最优值；调整前需要固定负载的重复性能对比。

## 6. 多任务同时下载时如何共享

假设当前设置为：

- 同时下载任务数：3；
- 单任务最大连接数：16；
- 全局 Range 连接预算：16。

当 3 个大文件同时下载时：

- 最多有 3 个任务处于下载状态；
- 每个任务都可以准备自己的 Range 工作块队列；
- 三个任务的活动 Range 数据请求合计最多为 16，而不是 `3 x 16 = 48`；
- 预算不会固定切成三份，任务会随工作完成、暂停、失败和连接升降释放或取得可用额度；
- 一个任务完成或降低连接数后，释放的额度可以被其他等待中的任务使用。

普通单通道 GET、能力探测和 HLS 请求不占用这 16 个 Range 数据请求额度，因此进程的网络请求总数可能高于 16。它们仍受同时下载任务数、文件描述符、响应缓冲、速度限制和系统网络栈约束。

## 7. 暂停、恢复和设置变更

- 暂停时会停止当前请求并保存已完成的进度，活动资源随之释放。
- 恢复 Range 任务时继续处理原有工作块中尚未完成的部分，不重新拆分整个文件。
- 已经存在 Range 工作块的任务会保留 Range 恢复路径；之后关闭 HTTP Range 下载，只影响尚未创建工作块的新任务。
- 修改连接上限可以影响任务下一次启动时允许使用的活动连接数，但不会把已有工作块重新切成另一种布局。
- 恢复前会核对文件大小和服务器提供的资源标识；资源已经变化时应停止恢复，避免把不同版本的内容写进同一个文件。

保留原布局的优先级高于按新设置重新分片，因为可验证的续传正确性比重新追求理论上的最优分片更重要。

## 8. HLS 与 HTTP Range 的区别

HLS 播放列表本身包含按播放顺序排列的媒体分片，但这些媒体分片不是 HTTP 文件的 Range 工作块。

当前 HLS 处理流程是：

```text
读取播放列表
  -> 按顺序下载媒体分片
  -> 按顺序追加到目标文件
  -> 保存已完成的连续位置
```

HLS 媒体分片当前按顺序逐个下载，不使用 HTTP Range 的单任务连接上限和全局 Range 预算。它仍与其他任务共享同时下载任务数、全局速度、缓冲、重试和文件描述符等资源约束。

## 9. 界面与文档用词

| 场景 | 推荐用词 | 避免用词 |
| --- | --- | --- |
| 全局或任务设置 | 单任务最大连接数、最大连接数 | 线程数、分片线程数 |
| 同时运行的任务 | 同时下载任务数 | 总线程数 |
| 文件的字节范围列表 | Range 工作块 | 连接数、线程数 |
| 实时网络活动 | 当前活动 Range 请求 | 用工作块总数冒充当前连接数 |

进度界面可以同时显示“最大连接数”和“Range 工作块”，但两者必须分开。只有取得真实运行数据时才显示“当前活动 Range 请求”；不能根据工作块总数推算它。

推荐的用户解释是：

> 当前任务最多使用 16 个连接，并准备了 64 个 Range 工作块。连接完成一个工作块后会继续处理下一个；所有任务的 Range 请求合计受全局预算限制。

## 10. 性能边界

更多连接只在单连接受限、服务器正确支持 Range、文件足够大且本地写入没有成为瓶颈时可能提高速度。连接增加也会带来更多请求调度、内存缓冲、文件描述符、TLS/HTTP 处理、乱序写入和服务端压力。

因此当前策略不是追求“连接越多越快”，而是：

```text
小文件保持简单
  + 大文件准备足够的可领取工作块
  + 活动连接逐步试探并允许回退
  + 多任务共享固定资源预算
  + 用相同负载的重复测试决定是否调整默认值
```
